How Providers Fit Together

1. Register tenants Create tenant records that scope workload profiles, secret backends, and model entitlements.
2. Store credentials Pick an AI provider (OpenAI, Anthropic, Cursor…), register a secret backend (db/Vault/AWS), then store the API key.
3. Bind consumers Link stored credentials to agents, gateway, or routes via Credential Bindings (or the Cursor gateway shortcut).
4. Publish models Register model IDs (e.g. gpt-4o-mini) under each AI provider; grant tenant entitlements.

Three Layers — Do Not Mix These Up

Secret backend Where keys are stored: db, Vault, AWS SM, Azure KV. Used in Onboard Secret Provider only.
AI provider Which vendor API you call: OpenAI, Anthropic, Cursor, AWS Bedrock. Used when storing keys, bindings, and model catalog.
Model ID Which LLM to run: gpt-4o-mini, claude-3-5-sonnet. Registered under an AI provider in Models & Entitlements.

When should I use workload identity vs secret providers?

Workload identity is for short-lived access tokens exchanged at runtime (agents calling cloud APIs without embedding long-lived secrets). Secret providers are for reading and renewing secret material (API keys, Cursor tokens in db or external vaults, database credentials). Many deployments use both: workload identity for compute federation and secret providers for key vault access.

Tenant Directory

Tenants are the top-level scope for all provider resources. Create or edit a tenant before onboarding. Use Deactivate to retire — there is no hard delete.

1. Define tenant Choose ID, display name, and type (enterprise, regulated, sandbox).
2. Save Creates or updates the tenant record used by provider pickers.
3. Deactivate when done Use Deactivate in Tenant Records, or set Status to inactive when editing. Reactivate restores onboarding access.
Deactivate vs delete

Tenants cannot be deleted because workload profiles, secret providers, and entitlements may still reference them. Deactivating blocks new provider onboarding for that tenant while preserving audit history. Existing provider records tied to the tenant remain visible in their lists.

Onboard Workload Identity Provider

Register a federated identity profile for short-lived tokens without storing long-lived cloud credentials.

AI vendor credentials (OpenAI, Anthropic, Cohere, …)

Workload profiles for AI vendors do not store API keys in this form. Production deployments inject short-lived tokens at runtime via environment variables such as OPENAI_WORKLOAD_IDENTITY_ACCESS_TOKEN, ANTHROPIC_WORKLOAD_IDENTITY_ACCESS_TOKEN, and similar prefixes per vendor. Use Test and Exchange Token after ops configures the sidecar or host env. For platform-encrypted storage instead, create a db secret provider and use Store Secret Value with refs like providers/openai/api-key.

Field reference — workload identity onboarding
  • Audience — Token audience expected by the cloud STS or identity endpoint (e.g. sts.amazonaws.com).
  • Role ARN / Equivalent — IAM role or cloud role binding the workload may assume.
  • Subject patterns — JSON list of allowed subject prefixes (e.g. ["agent-*"]).
  • Session TTL — Maximum token lifetime in seconds (60–86400).

Examples: ["agent-*", "team/platform/*"] | ["service-account:build-*", "org/dev/*"]
